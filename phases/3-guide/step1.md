# Step 1: docs

## 읽어야 할 파일

- `/AGENTS.md` — CRITICAL 규칙 전체(정본). **이 내용이 `CONVENTIONS.md` 로 옮겨져야 한다**. `CLAUDE.md` 는 이 파일을 가리키기만 하는 5줄짜리라 읽어도 규칙이 없다
- `/docs/ARCHITECTURE.md`, `/docs/ADR.md`, `/docs/UI_GUIDE.md` — 하네스 가드레일. 사람이 읽을 문서로 재구성할 원본
- `/tools/check.js` — 자동 검증이 무엇을 잡고 무엇을 못 잡는지 파악하라. **못 잡는 것이 수동 체크리스트 항목이 된다**
- `/src/assets/scss/base/_reset.scss` — iOS 대응이 실제로 어떻게 들어갔는지. 크로스브라우징 문서의 근거
- `/src/assets/js/util/api.js` — `data-bind` 규약이 주석에 정의되어 있다
- `/src/guide.html` — 이전 step 생성물. 문서에서 참조한다

## 배경

`.claude/` · `.codex/` 를 삭제하고 `AGENTS.md` 를 걷어내는 순간 `AGENTS.md` + `docs/*.md` 가 주던 가드레일이 전부 사라진다. **이 step은 그 지식을 사람이 읽는 문서로 옮기는 작업이다.** 현업에서 손으로 작업할 때 이 문서들이 유일한 규칙이 된다.

프로젝트 루트에 만든다 (`docs/` 는 하네스 레이어라 걷어낼 때 함께 삭제된다).

## 작업

### 1. `CONVENTIONS.md` — 코딩 컨벤션

`AGENTS.md` 의 CRITICAL 규칙을 사람이 읽는 형태로 옮기고, 아래를 추가한다.

**(1) 레이어 규칙**
`util/` → `common/` → 엔트리. 각 레이어에 무엇을 두고 무엇을 두지 않는지, **왜 그런지**까지 적는다. 이유를 모르면 규칙이 지켜지지 않는다.

**(2) 네이밍 규약**
- CSS 클래스 방법론(BEM 등)을 하나 정해 명시한다. 실제 컴포넌트에서 쓴 것과 일치시켜라
- 파일명, `data-*` 속성명 규칙

**(3) Figma → 코드 변환 가이드** ★ 계약 우대사항 대응

오토레이아웃 → Flexbox 대응표를 만든다:

| Figma | CSS |
|---|---|
| Auto layout 세로/가로 | `flex-direction: column / row` |
| Gap | `gap` |
| Padding | `padding` |
| Align / Distribute | `align-items` / `justify-content` |
| **Hug contents** | `width: fit-content` (또는 기본값) |
| **Fill container** | `flex: 1` 또는 `width: 100%` |
| **Fixed** | 고정값 — **되도록 피하고 max-width로** |
| Absolute position | `position: absolute` — 남용 주의 |

Figma 변수/토큰 이름 → CSS 변수 이름 매핑 규칙도 정한다 (예: `color/text/body` → `--color-text-body`).

**(4) 컴포넌트 추가 절차**
새 컴포넌트를 만들 때 무엇을 해야 하는지 단계로 적는다: fragment 생성 → `@component` 주석 → SCSS → 엔트리 연결 → `node tools/build.js` → 가이드·스니펫 자동 반영 확인.

**(5) 개발사 연동 규약**
`data-bind` 규약 전체를 정리한다. 개발사가 읽을 부분이므로 예시를 충분히 넣는다.

**(6) 웹폰트 도입 절차** ★ 계약 우대사항(웹 퍼포먼스 최적화) 대응

현재 이 프로젝트는 시스템 폰트만 쓴다 (`--font-family-base`). 시안 수령 후 웹폰트가 확정됐을 때 **무엇을 어떤 순서로 해야 하는지**를 절차로 적는다. 한글 웹폰트는 서브셋 없이 2~5MB라 이 항목 하나가 성능 지표를 좌우하므로, 질의 단계에서 놓치면 되돌리기 비싸다.

최소한 아래를 포함한다:

- **라이선스 확인이 1순위** — 웹 사용(webfont) 권한이 포함되는지. 데스크톱 라이선스만 보유한 폰트를 웹에 올리면 계약 위반이다. 이건 기술 문제가 아니라 법무 문제이므로 착수 전에 끝내야 한다
- **한글 서브셋 필수** — 전체 글리프는 2~5MB, 서브셋 시 수십~수백 KB. 서브셋 도구가 폐쇄망에 반입 가능한지도 함께 확인한다 (사내 반입 승인이 오래 걸릴 수 있다)
- **포맷**: `woff2` 우선, 필요 시 `woff` 폴백. `tools/serve.js` MIME 목록에 `woff2` 가 이미 등록되어 있다
- **`font-display: swap`** — FOIT(폰트 로드까지 텍스트가 안 보임) 대신 FOUT(폴백으로 먼저 보이고 교체)를 택한다. 이커머스에서 텍스트가 안 보이는 시간은 그대로 이탈이다
- **`<link rel="preload" as="font" type="font/woff2" crossorigin>`** 로 본문 폰트 1개만 우선 로드한다. `crossorigin` 을 빠뜨리면 preload가 무시되고 두 번 받는다 — 가장 흔한 실수다
- **파일 위치**: `src/assets/font/`. `@font-face` 선언은 `src/assets/scss/base/_fonts.scss` 한 곳에 모은다
- **교체 지점은 `--font-family-base` 하나** — `tokens/_typography.scss` 의 이 변수만 바꾸면 전체가 따라온다 (ADR-004)

`DESIGN_REVIEW.md` 의 폰트 질의 항목과 이 절차를 **상호 참조**시킨다. 질의에서 "웹폰트 쓴다"는 답이 나오면 곧장 이 절차로 넘어올 수 있어야 한다.

### 2. `DESIGN_REVIEW.md` — 시안 검토 체크리스트 ★ 계약 주요업무 1번 대응

Figma 시안을 받았을 때 **퍼블리싱 착수 전에 확인하고 질의할 항목**이다. 실무에서 이 단계를 건너뛰면 작업 중반에 막힌다.

최소한 아래를 포함한다:

- **상태 정의**: hover / focus / active / disabled / loading / error / 선택됨 이 정의되어 있는가? (대개 빠져 있다)
- **빈 상태**: 검색 결과 없음, 장바구니 비어있음, 주문 내역 없음
- **극단값**: 상품명이 아주 길 때, 가격이 8자리일 때, 리뷰가 0개일 때, 옵션이 20개일 때
- **브레이크포인트별 시안**: PC/MO 둘 다 있는가? 태블릿 구간은?
- **폰트**: 웹폰트인가? **라이선스가 웹 사용을 허용하는가?** 한글 웹폰트는 용량이 크니 서브셋 계획은?
- **이미지**: 2x 에셋이 있는가? WebP 변환 가능한가? 상품 이미지 종횡비가 통일되어 있는가?
- **인터랙션 명세**: 캐러셀 자동재생 여부·간격, 애니메이션 duration, 스크롤 동작
- **접근성**: 색상 대비가 4.5:1을 만족하는가? (`guide.html` 토큰 표에서 즉시 확인 가능) 색상만으로 정보를 전달하는 곳은 없는가?
- **무한 스크롤 요구 시**: 키보드로 푸터 도달 문제와 뒤로가기 위치 복원 문제를 어떻게 처리할지
- **계약 미확정 항목**: 대상 해상도 구간, QA 수정 요청 반영 횟수·기간

각 항목에 **왜 물어야 하는지**를 한 줄로 붙인다. 그래야 질의할 때 근거가 된다.

### 3. `QA_CHECKLIST.md` — QA 점검 항목 ★ 계약 주요업무 대응

1차 QA와 수정 대응에 쓴다. 자동 검증(`check.js`, axe)이 **못 잡는 것** 위주로 구성한다.

- **키보드**: 모든 인터랙티브 요소 도달 가능, 포커스 표시 보임, 포커스 순서가 시각 순서와 일치, 모달에서 트랩·Esc·복귀
- **확대**: 브라우저 200% / 400% 확대 시 콘텐츠 손실 없음, 320px 상당에서 가로 스크롤 없음 (WCAG 1.4.10)
- **색상 무관**: 흑백으로 봐도 모든 정보가 전달되는가 (에러/성공/필수/품절/할인)
- **극단값**: 긴 상품명, 큰 금액, 빈 목록, 이미지 로드 실패
- **상태**: 로딩·빈·에러 상태가 모든 목록형 영역에 있는가
- **실기기**: iOS Safari 하단 고정 요소가 홈 인디케이터에 안 가리는가, 입력 포커스 시 확대 안 되는가
- **페이지별 항목**: 7개 페이지 각각의 고유 점검 사항

### 4. `CROSSBROWSER.md` — 크로스브라우징 대응표 ★ 계약 필수요건 대응

대상: iOS Safari, Android Chrome 최신 2개 버전.

`base/_reset.scss` 에 실제로 들어간 대응을 **증상 → 원인 → 해결** 형식으로 정리한다:

| 증상 | 원인 | 해결 |
|---|---|---|
| 입력 포커스 시 화면 확대 | iOS Safari는 16px 미만 입력에 줌 | `font-size: 16px` 이상 |
| 하단 고정 요소가 가림 | 홈 인디케이터 영역 | `env(safe-area-inset-bottom)` |
| `100vh` 가 화면보다 큼 | iOS 주소창 높이 | `100dvh` (폴백 병기) |
| 터치 시 회색 박스 | 기본 탭 하이라이트 | `-webkit-tap-highlight-color: transparent` |
| ... | ... | ... |

실제 작업 중 발견한 이슈를 계속 추가하는 문서임을 명시한다.

### 5. `README.md` 갱신

`3-guide` 단계의 산출물(`guide.html`, 스니펫)과 위 문서들로의 링크를 추가한다. 현업 도착 후 **가장 먼저 확인할 항목**(Node 버전, 사내 npm 미러 유무, sass 바이너리 OS)을 체크리스트로 넣는다.

## Acceptance Criteria

```bash
node tools/build.js
node tools/check.js
```

## 검증 절차

1. 위 AC 커맨드를 실행한다.
2. 각 문서를 처음 읽는 사람 관점에서 검토한다: **이 문서만 보고 컴포넌트를 하나 추가할 수 있는가?**
3. `CONVENTIONS.md` 의 규칙이 실제 코드와 일치하는지 표본 확인한다. 문서와 코드가 어긋나면 문서를 고쳐라.
4. `DESIGN_REVIEW.md` 의 항목이 실제로 질의 가능한 형태인지 확인한다 (근거가 붙어 있는가).
5. 결과에 따라 `phases/3-guide/index.json` 의 해당 step을 업데이트한다 (completed / error / blocked + 사유).

## 금지사항

- **`docs/` 폴더에 이 문서들을 만들지 마라.** 프로젝트 루트다. 이유: `docs/` 는 하네스 레이어라 걷어낼 때 함께 삭제되며, 그러면 현업에 규칙이 남지 않는다.
- **규칙만 적고 이유를 빼지 마라.** 이유를 모르는 규칙은 지켜지지 않고, 상황이 바뀌었을 때 판단할 근거도 없다.
- **자동 검증이 이미 잡는 항목으로 QA 체크리스트를 채우지 마라.** 사람이 확인해야만 하는 것 위주로 구성한다.
- **`AGENTS.md` 를 그대로 복사하지 마라.** 프롬프트용 문서와 사람이 읽는 문서는 구성이 다르다.
- 코드를 수정하지 마라. 이 step은 문서 작업이다. 문서와 코드가 어긋나면 **문서를 코드에 맞추고** 불일치를 summary에 기록하라.
